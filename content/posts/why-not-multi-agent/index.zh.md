## 背景

我从零搭建了一套量化研究系统，覆盖从数据采集到模拟盘的完整链路：

```
数据采集 → 因子研究 → 反过拟合检验 → ML训练 → 泄漏检测 → 回测 → 信号生成 → 模拟盘
```

这套系统分三层：Research Kernel（执行引擎）、AI Orchestration（编排层）、Human Interface（展示层）。AI 的角色是驱动研究流程自动迭代——生成因子表达式、提交回测、评估指标、决定是否继续优化。

当我决定加入 AI 编排层时，第一个架构问题就是：用多智能体还是单智能体？

## 多智能体的诱惑

Multi-Agent 是当前 AI 工程的热门范式。直觉上，量化研究似乎很适合拆成多个 Agent：

- **研究 Agent**：负责生成因子表达式和策略代码
- **回测 Agent**：负责提交回测、收集结果
- **评估 Agent**：负责分析指标、判断是否过拟合
- **风控 Agent**：负责检查约束条件

看起来很合理——分工明确，各司其职。

## 为什么没有这么做

我最终选择了单 Agent + 状态机编排。不是因为"多智能体太难实现"，而是因为在我的场景里，多智能体的前置条件都不满足。

### 条件一：不同任务需要不同工具集

多智能体的一个核心前提是每个 Agent 有自己的专属工具，工具集之间不重叠。

但在量化研究里，所有操作最终都指向同一套 Kernel API：

```
研究 Agent → 调 Kernel API 提交因子研究
回测 Agent → 调 Kernel API 提交回测
评估 Agent → 调 Kernel API 查询指标
风控 Agent → 调 Kernel API 检查约束
```

四个 Agent 用的是同一把锤子。拆开不增加能力，只增加协调成本。

### 条件二：任务可以并行

多智能体的第二个前提是 Agent 之间可以并行工作，通过协调实现 1+1>2。

量化研究的流程是**严格串行**的：

```
训练 → 回测（依赖模型）→ 评估（依赖回测结果）→ 决策（依赖评估）
```

你不可能在没有训练好模型的情况下跑回测，不可能在没有回测结果的情况下做评估。每一步的输入都是上一步的输出。并行没有空间。

### 条件三：存在需要辩论或对抗的场景

有些系统用多 Agent 实现"红蓝对抗"——一个 Agent 提出方案，另一个 Agent 专门找漏洞。在某些开放性任务（如方案设计、文本生成）里这很有价值。

但量化研究的评估是**数值确定的**。一个因子的 Sharpe Ratio 是 1.2 就是 1.2，IC 是 0.03 就是 0.03。不需要另一个 Agent 来"辩论"这个数字是否正确——它就是一个数。反过拟合检验也是确定性的四项检查，不是主观判断。

对抗机制在这里退化成了 if-else 判断，单 Agent 内部就能做。

## 我选择的方案：单 Agent + 状态机

```
INIT → PLAN → GENERATE_CODE → EXECUTE → EVALUATE → ITERATE/FINISH
                                  ↑          │
                                  └──────────┘
```

一个 Agent 驱动整个循环，状态机控制行为边界：

- **GENERATE_CODE**：Agent 调用 LLM 生成因子/策略代码
- **EXECUTE**：通过 Kernel API 执行回测
- **EVALUATE**：评估指标，和阈值对比，做出 continue/stop 决策
- **ITERATE**：如果不满意，带着上一轮的指标反馈回到 GENERATE_CODE

每次迭代都有完整记录：代码、指标、评估决策、原因。可以追溯任何一个决策是怎么做的。

### 为什么状态机比多 Agent 更适合

| 维度 | 多 Agent | 单 Agent + 状态机 |
|------|---------|-----------------|
| 上下文 | Agent 间需要显式传递，容易丢失 | 天然共享全部上下文 |
| 调试 | 跨 Agent 日志追踪 | 单进程内线性追踪 |
| 延迟 | Agent 间通信开销 | 零通信开销 |
| 归责 | 哪个 Agent 做了错误决策？ | 状态机记录每步决策 |
| 复杂度 | N 个 Agent × M 种通信模式 | 1 个 Agent × K 个状态 |

核心论点：**当流程是串行的、工具集是共享的、评估是确定性的，多 Agent 增加的复杂度没有被任何收益抵消。**

## 什么时候多智能体是正确选择

我不是说多智能体没有价值。它在以下场景是正确的：

1. **任务天然并行**：比如同时搜索多个信息源，每个 Agent 负责一个源，最后汇总。工具集不同，并行有收益。

2. **需要主观判断的对抗**：比如写作任务——一个 Agent 写，一个 Agent 从读者视角挑刺。评判标准不是数值而是质量，对抗有价值。

3. **工具集不可共享**：比如一个 Agent 只能访问代码库，另一个只能访问生产环境。权限隔离要求物理分离。

4. **规模扩展**：同一类任务需要同时处理大量实例，每个 Agent 处理一个实例。这本质上是并发而不是"多智能体"，但框架层面用多 Agent 实现是合理的。

我的量化研究系统**一条都不满足**。

## 对"多智能体热"的看法

当前行业有一种倾向：把多 Agent 当作一种"更高级"的架构范式，仿佛系统里 Agent 数量越多越先进。这和微服务架构的演进类似——2015 年前后，所有人都在拆微服务，直到发现很多系统根本不需要拆。

选择架构的标准不是"新不新"或"热不热"，而是"问题结构是否匹配"。

我的问题结构是：串行流程、共享工具、确定性评估。答案是单 Agent + 状态机。

如果你的问题结构不同，答案可能也不同。关键是先分析问题结构，再选架构，而不是反过来。
